# 交易持久化阻塞与孤立持仓恢复

## 问题

- 卖出成交更新 CA 冷却时间时，PostgreSQL 参数没有明确转换为 `timestamptz`，导致整个成交事务回滚。
- 异步持久化器只有一个消费循环，失败任务原地无限重试会阻塞后续所有信号、订单和成交记录。
- 链上买入及 Redis 持仓已经成功、数据库买入信号尚未落库时，候选项目会停在 `bought`，但无法继续执行卖出判断。

## 调整

- 冷却时间计算显式使用 `timestamptz + interval`，保证成交、订单、持仓和 CA 风控在同一事务内提交。
- 单个持久化任务失败后延迟 `2s` 重新入队，让后续任务继续执行；失败任务仍持续重试，不静默丢弃。
- 信号或订单依赖记录尚未创建时，更新操作返回错误并重新入队；订单一旦进入 `filled`，延迟到达的 `submitted` 或 `failed` 更新不能再把成交状态降级。
- Redis 持仓存储增加账户级未平仓列表读取。服务启动时将 PostgreSQL 和 Redis 的未平仓持仓合并到运行时。
- 候选池查不到数据库买入信号时，只在 Redis 明确存在对应未平仓持仓后恢复卖出监控；不存在 Redis 持仓时继续等待，不重新买入。
- 从 Redis 恢复时使用实际平均成交价乘以 token supply 计算入场市值；卖出策略继续保留候选状态里的入场 K 线时间，避免用带秒数的成交时间破坏 K 线定位。

## 验证

- SQL mock 校验冷却时间参数包含显式 `timestamptz` 转换。
- 异步持久化测试覆盖永久失败任务不会阻塞后续任务。
- Redis 持仓测试覆盖只回载 `open` 状态。
- 候选监控测试覆盖数据库信号缺失、Redis 持仓存在时仍能触发卖出。
