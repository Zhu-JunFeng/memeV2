# 外部服务与服务器资源 TG 告警

> API Key 与限流告警规则已被需求变更 032 覆盖：普通 `429` 和单个 Key 鉴权失败不直接发送 TG，只有 Key 池可用率严格低于 `50%` 才告警。

## 目标

新增一个与交易策略完全独立的运行告警功能。当外部服务或生产服务器出现持续异常时，通过现有 Telegram 机器人通知，不改变数据源选择，不添加备用数据源，也不阻断当前业务流程。

## 外部服务告警

覆盖以下外部调用：

- GMGN K 线与报价
- GMGN 已毕业项目源
- XXYY 已毕业项目源
- Birdeye K 线与交易明细
- Bitquery 交易明细
- DexScreener 报价
- Solana RPC
- Jupiter 报价、下单与执行

告警规则：

- HTTP `401/403` 或 JSON 顶层业务码 `401/403`：不直接告警，由 Key 池整体可用率规则判断。
- HTTP `429` 或 JSON 顶层业务码 `429`：正常执行 Key 冷却/轮换，不发送 TG 告警。
- GMGN 或 Birdeye Key 池可用率严格低于 `50%`：发送 TG 告警。
- 网络错误、超时或其他 HTTP `4xx/5xx`：连续 `3` 次后告警。
- 从发起请求到响应体读取完成达到 `3s`：连续 `3` 次后告警。

## 服务器资源告警

- 每 `30s` 读取 Linux `/proc/stat` 计算整机 CPU 使用率。
- 每 `30s` 读取 Linux `/proc/meminfo`，按 `MemTotal - MemAvailable` 计算整机内存使用率。
- CPU 或内存连续 `3` 次达到 `85%` 后发送 Telegram 告警。

## 去重与恢复

- 同一服务、同一异常类型独立计数。
- 同类告警发送后进入 `10` 分钟冷却期，冷却期内不重复刷屏。
- 告警激活后连续 `2` 次检测正常，发送一条恢复通知。
- Telegram 通知通过独立队列异步发送；队列或 Telegram 异常不会影响外部请求和交易执行。

## 默认配置

```yaml
alert:
  enabled: true
  latency_threshold_ms: 3000
  consecutive_failures: 3
  consecutive_high_latency: 3
  recovery_successes: 2
  cooldown_seconds: 600
  resource_check_interval_seconds: 30
  resource_consecutive_samples: 3
  cpu_threshold_percent: 85
  memory_threshold_percent: 85
```
